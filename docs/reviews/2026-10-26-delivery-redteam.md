## Findings

### P1 / RT1：不同 excluded key 重複使用同一份合資格餘額，造成少收

- 位置：`bundle.js:53`、`bundle.js:58`、`bundle.js:68`，`calculateCouponDiscount()`。
- 前置條件：訂單有不同排除集合的兩張券。測試使用程式／儲存資料結構接受的非預設券快照；目前預設 UI 只有紅券的一種排除集合，不宣稱一般預設點選必然觸發。
- 最短重現：開瓶器 100、滴膠貼紙 60、扭蛋兩抽 1200；兩券額度各 100，excluded 分別為 `["epoxy_sticker"]` 及 `["epoxy_sticker", "not_in_order"]`，然後結帳。第二集合只是多排除一個不在訂單中的商品，兩券實際都只能折開瓶器。
- 手算預期：1360 - 100 = **1260**。開瓶器的 100 只能折一次，貼紙 60 必須保留收費。
- 實際：兩 key 各初始化 100 的獨立餘額，折抵相加後又用「不套用 excluded」的 160 上限裁切，成交 **1200**，少收 **60**；持久化 money 與 sale.total 都是 1200，統計另外產生 -60 的歷史調整。
- 證據：`tests/redteam-delivery.test.cjs:25`，執行 `node --test tests/redteam-delivery.test.cjs`：`1200 !== 1260`；RT1 evidence 印出實際 money、total 及統計列。這是經正式結帳／儲存函式產生的虛擬新交易，不是只測純計價結果。
- 歸屬：既有缺陷，main 同樣存在；`git blame` 指向 `a7b57f67` 的抵用券池設計，不是福袋搬移／隱藏提示新引入。
- 最小建議：讓不同券共用每個合資格品項的剩餘可折抵額度，不能只按 excluded key 分池及使用無條件總上限；若不支援這類舊券，應明確拒絕，不能接受後錯誤收銀。不直接修改歷史已付款總額。

### P2 / RT2：可完整歸屬的新交易，被貪婪統計分攤偽裝成歷史差額

- 位置：`render.js:198`、`render.js:203`、`render.js:209`、`render.js:219`，`getSaleStatistics()`。
- 前置條件：兩個各 100 元的商品 A（開瓶器）及 B（虛擬自訂商品）、兩次扭蛋 1200；先放一張可折 A/B 的 150 元券，再放只能折 A 的 50 元券。與 RT1 相同，這是非預設但資料結構允許的券快照。
- 最短重現：按上述順序加入、透過 `finishGashapon()` 及 `checkoutCurrentSale()` 成交，再讀商品營收統計。
- 手算預期：限品券折 A 50，一般券折 A 50 + B 100；因此 A=0、B=0、扭蛋=1200，且不需要任何歷史調整。
- 實際：一般券先按比例分攤 A/B 各 75，限品券只能再歸屬 A 剩餘 25；統計變為 **A=0、B=25、扭蛋=1200、歷史調整=-25**。成交額 1200 正確，但商品排行錯誤，調整列掩蓋了可修正的新訂單分攤問題。僅核對最終加總會漏掉。
- 證據：`tests/redteam-delivery.test.cjs:38`，RT2 evidence 直接印出新交易統計；斷言 `25 !== 0` 失敗。
- 歸屬：`a82bc975` 統計修正引入，已合併於 main；不是最新 CSV 顯示修改造成。
- 最小建議：在彙總前求符合各券資格及額度的可行分配，必要時調整先前廣券的分配；本案先處理窄券即可得到正確解。不能將演算法分配不足自動當作快照不足。

### P2 / B5：相同資產版本允許有效快取舊程式恢復已移除的 CSV 提示

- 位置：`index.html:85`，仍使用 `storage.js?v=raffle-csv-1`；對應隱藏介面為 `index.html:21`、`index.html:22`。
- 前置條件：瀏覽器仍持有移除提示前的有效 HTTP script cache，而 HTML 已更新。只在隔離本機重現，沒有探測正式站目前的快取標頭或使用者 cache。
- 最短重現：本機 server 先提供 `9846a488` 的 HTML/storage.js，為 script 設定合法 `Cache-Control: public, max-age=3600`，HTML 為 no-store；開啟後關閉分頁。server 切到本次新版，在同一隔離 browser context 新開分頁並匯出虛擬訂單。這不是覆寫 JS 方法來假造顯示，而是原生 Chromium HTTP 快取。
- 預期：成功提示及可見下載連結均不恢復。
- 實際：script 只向 server 請求一次舊版，新頁沒有重新取得新版 storage.js；成功下載後，舊文字 **「CSV 已產生；若未開始下載，請點下載連結。」** 再次可見。下載本身成功，這不是已證實的檔案下載失敗。
- 證據：`tests/redteam-delivery-browser.cjs:110`（B5）：`{"requests":["old"],"message":"CSV 已產生；若未開始下載，請點下載連結。","visible":true}`，預期 false 的斷言失敗。多次獨立 context 執行均重現。
- 歸屬：CSV 隱藏更新未同步更新 script URL 的更新相容性回歸（PR #26），目前 main 同樣存在。純淨無舊快取載入時不會出現。
- 最小建議：對 storage.js 使用新的版本／內容雜湊 URL，確保新 HTML 取得新程式；不要求使用者清除網站資料。未直接修改產品程式。

### RT1：共用優惠後容量與最大流

- `bundle.js` 新增純函式 `allocateCouponDiscount()`，回傳總折抵、每個商品／款式的容量與折抵、各券使用量及明細。

- 所有券共用商品容量；券面額為供給，資格為可連接邊。先保留可行的比例分攤，再以 Edmonds-Karp 殘餘路徑重新分配先前券的使用量，求最大可行流量；不是依限品券排序的貪婪解法，也不再按 excluded key 分池。
